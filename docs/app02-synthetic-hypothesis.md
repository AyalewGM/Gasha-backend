# APP-02 — change then unusual payment (synthetic hypothesis only)

Scope: the Product Owner's Dashen PoC candidate **UC-03 / APP-02**, under Issues #41 and #48. This is **not** a committed Bank detector, phishing/deception proof, a Bank-approved threshold, a case or readiness authority, or a payment action. All proposed metrics, change provenance, status, baseline and optional maintenance context are **caller asserted**.

The opt-in offline function `evaluate_app02_synthetic` reuses the merged `ScenarioObservation(APP-02)` field-coverage and dataset/tenant/installation binding. It does not add an API route, worker import, stored Bank evidence, signal service, scoring rule, readiness gate, external connection or enforcement. The existing decision, transport, tenant and case code are unchanged; merged #52/#53/#54 are untouched.

## Candidate contract and deterministic precedence

- Requires typed change kind (device, credential or security-profile), opaque source/version and change pseudonym, event-bound payment identity, time, amount/currency/status, proposed config/policy and a complete **pre-change** baseline with minimum samples. All four required change fields must share the claimed change source/version and change time; payment event/status/amount/currency must share one payment source/version and payment time. An unrelated source cannot be spliced into either event group. Payment event must match the observation. A source presence record or digest is **not** an attested Bank value.
- Every required source field must have been available by the claimed metrics snapshot, and metrics by the observation's cutoff. Future/post-cutoff facts cannot be used. Cross-tenant/dataset/event/policy/version substitution raises a contract error.
- A change **after** payment returns `blocked_future_change` rather than a synthetic alert or fabricated clean negative. An incomplete or post-change baseline blocks. Unknown/failed/reversed payments block. ETB/USD comparison without approved point-in-time FX blocks.
- Otherwise: outside the proposed change→payment window returns `change_outside_proposed_window`; ordinary value relative to the proposed floor or baseline returns `amount_not_unusual`. Only an otherwise qualifying signal may be contextualized by source-matched, observed, caller-reported approved maintenance/reset.
- If optional maintenance/reset context is not assessed, return `maintenance_context_unassessed` instead of asserting a clean positive or claiming an exclusion. If its absence was explicitly reported with matching source metadata, return `synthetic_change_then_unusual_payment_hypothesis`, never a fraud/APP/deception determination.
- The effective-input SHA-256 is a canonical, domain-separated **identity only**, sensitive to policy, metrics, source, timing and observation changes. It is not a signature, trusted registry record or approval.

## Evidence and limits

Tests cover successful/failed/reversed payments, each change kind, missing required evidence, after-snapshot and after-cutoff facts, old/after-payment changes, source and tenant substitution, approved reset, baseline and currency failures, exact threshold, UTC-equivalent times, mutated frozen objects, deterministic results and no protected runtime imports. Exact-head GitHub CI and independent Product Owner, Security/Architecture, Fraud Intelligence and QA verdicts are required before an internal integration decision.

To build a **Bank-facing** APP-02 detector, Dashen must authorize and supply versioned device/profile/credential events and payment feeds, source-attested change semantics, calibrated baseline and FX policy, legitimate maintenance provenance, complete historical windows, fraud-confirmation labels and a shared immutable cohort. The bank-aware adapter and feature builder must prevent future information and caller-chosen authority; separate Issue #49 independent trusted evidence and approvals must remain in force. Even a positive synthetic finding cannot request or execute a HOLD/BLOCK, freeze or payment interruption. No automatic claim of prevented loss or false-positive performance is supported.
