# Issue #48 — Eight-scenario batch coverage artifact (synthetic/inactive)

This increment aggregates the **existing** `ScenarioObservation` / `inspect_scenario_coverage` contract, without writing another detector or replacing the existing replay, report or #45 append-only case timeline. It follows the Product Owner's November 3 instruction to stop expanding synthetic detection scenarios and measure the eight already selected. The batch API is `inspect_scenario_coverage_batch(scope, tuple(observations)).to_dict()`.

This branch incorporates current main, including the already merged MM-02 PR #97; no MM-02 implementation is changed. The batch stores each scenario summary as a frozen typed value object, including an immutable coverage-rate record and tuples of field/count pairs. Each `to_dict()` call independently constructs fresh JSON-ready dictionaries and lists at all nested levels; mutable export aliases cannot rewrite retained counts or rates while preserving the input digest. `batch_digest` still identifies canonical input and is not an authentication signature.

The output separates ATO-02, ATO-06 (UC-01), MM-01, MM-02, MM-05 (UC-02), and APP-01, APP-02, APP-05 (UC-03). All eight appear even with zero records. For each scenario it reports a unique-event denominator, required-evidence complete/blocked counts, per-required-field missing counts and per-optional-field unavailable counts. Zero observations yield `value=null` and `undefined_reason=no_scenario_events` — never a fabricated 100% pass. Missing required data blocks only that scenario. Optional missing fields never become numerical zero-risk scores.

Input is a typed immutable tuple of caller-supplied, pseudonymized observation records. The existing point-in-time and field-evidence validator is invoked for each row. The batch enforces a single installation, tenant, dataset digest, source schema, mapping/config versions, collection window and report-as-of cutoff. Identical within-scenario duplicate event packets collapse to one denominator; conflicting packets with the same scenario/event identity reject the whole report. The canonical batch digest is invariant under input ordering, identical retries and equivalent UTC instants. It is a **consistency identifier, not a signature or Bank attestation**.

Only fixed scenario/field names, aggregate counts and caller-provided opaque scope/version strings appear in the JSON artifact. No raw event/customer/beneficiary/device IDs, field evidence digests, transfer amounts, case details or row-level outcomes are exported. The output always asserts `bank_data_verified=false`, `historical_replay_authorized=false`, `detection_executed=false`, `readiness_authorized=false`, `enforcement_activated=false`.

**UC-04 prioritization and UC-05 false-positive reduction are explicitly BLOCKED**, with null confusion-count/rate placeholders. Real prioritization requires the #45 append-only analyst disposition/outcome contract, an approved alert budget and authenticated alert/case joins; UC-05 requires mature, consistently timed labels and a comparable Gasha/incumbent cohort through existing #48 replay/report infrastructure. This batch artifact does not perform those joins, mark Bank data covered, or satisfy Issue #49. In particular, merged PR #54's caller-asserted advisory `ready` never grants authority. Only a later independently reviewed adapter may bind bank-verifiable data, immutable cohort and case outcomes to the report.

Test with `pytest -q tests/test_poc_scenario_coverage_batch.py`. Independent PO, Security/Architecture and QA exact-head review is required before internal integration. No operational path, Bank integration, deploy, live identity, readiness or payment action is changed.
