# ATO-02 — new device with abnormal session activity (inactive synthetic hypothesis)

**Issue:** #48 (scenario/field contract), #41 (PoC traceability). **Use case:** UC-01. This module is deliberately offline and caller-asserted: it does not perform Bank fraud detection, prove account takeover, trigger intervention, provide regulatory evidence or satisfy the #49 readiness gate.

## Proposed semantics and required provenance

- The versioned `ScenarioObservation` must contain observed authentication outcome, device pseudonym, device-first-seen, known-device status, device lookback and session-anomaly field evidence, with matching tenant/installation/dataset and no post-decision-cutoff values. Every required observed field must also be available by the separate metrics snapshot time; evidence arriving later blocks evaluation (exact equality is allowed). The separate metrics' digest binds to that exact observation, and its authentication timestamp matches the observed event time.
- Known versus new device is derived from a **caller-claimed complete, continuous point-in-time device session history**, ending at the authentication event. A nonzero prior session count in the same device history produces an explicit known-device negative; missing/incomplete/gapped history **blocks**, never reports an innocent or new device.
- The tentative new-device temporal window and minimum lookback duration are **proposed** policy fields, not approved Bank thresholds. An old first-seen record or ordinary session produces an explicit negative. Unavailable anomaly evidence blocks; a failed or unresolved challenge is not a successful suspicious login.
- Reported approved reset/re-enrolment is an explicit contextual exclusion only for an otherwise qualifying successful-authentication, abnormal-session, new-and-recent device candidate, matched to a separately observed, source/version/time-bound optional `approved_device_reset` field available before authentication. The decision order is input/cutoff and snapshot evidence validation → continuous history → auth success → anomaly presence → known-device/ordinary-session/old-first-seen negatives → contextual reset exclusion → synthetic hypothesis. An unknown reset state remains explicitly unassessed and is **not** presumed absent.
- Fields and history remain untrusted assertions; the SHA-256 effective-input digest is for deterministic change detection, not a signature, attestation or authorized source. The output intentionally omits pseudonymous device/customer/account IDs and includes `bank_verified=false`, `fraud_determined=false`, `readiness_authorized=false` and `enforcement_activated=false`.

## Acceptance boundaries

Synthetic regression tests cover the 144-way reset/auth/anomaly/known/recent precedence cross-product, six required-field snapshot-arrival boundaries with positive and negative contexts, new/known device, ordinary/abnormal session, recent/old first-seen, complete/incomplete history, failed/challenged login, legitimate reset/re-enrolment, missing required evidence, wrong tenant/dataset, post-cutoff data, mutated frozen assertions and policy/version digest drift. This candidate remains **unwired** to the protected FastAPI app, durable worker, scorer, case management, readiness evaluator or payment enforcement.

Prior to operational development, the Bank must approve device-identification semantics, source authentication and device lifecycle history, history-completeness proof, suspicious-session features and thresholds, context rules for resets/new device enrolment, privacy/retention limits, point-in-time audit, labelled detection cohorts and human review of false positives. Account takeover and social engineering are separate claims, never inferred merely from a device/session heuristic. Independent PO, Security/Architecture, Fraud Intelligence and QA exact-head review is required.
